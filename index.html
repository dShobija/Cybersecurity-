1. Abstract

This project demonstrates the design, deployment, and validation of a network-based Intrusion Detection System (IDS) using Snort, aimed at detecting directory traversal attacks against a web server. A two-machine virtual lab was built using Oracle VirtualBox, consisting of an Ubuntu Server hosting an Apache2 web application (the target) and a Kali Linux workstation acting as the attacker. Snort was installed and configured on the target host, and a custom detection rule was written to identify directory traversal patterns in incoming HTTP traffic. An attack was then simulated from the attacker machine using a crafted HTTP request, and the IDS successfully detected and logged the intrusion attempt in real time.

2. Objectives

  • Set up a two-node isolated virtual lab environment for offensive/defensive security practice
  • Deploy and configure a web server (Apache2) as a monitored target
  • Install and configure Snort IDS on the target host for network traffic inspection
  • Author a custom Snort rule capable of detecting directory traversal attack patterns
  • Simulate a real-world directory traversal attack from an attacker machine
  • Validate that the IDS accurately detects and logs the simulated attack in real time
  • Document the exercise as a reusable, repeatable methodology for future detection-engineering practice

4. Lab Topology

The lab consists of two virtual machines connected over an isolated VirtualBox network. The Ubuntu Server (10.0.2.10) hosts the Apache2 web service and runs the Snort IDS, monitoring all inbound traffic on interface enp0s3. The Kali Linux machine (10.0.2.11) acts as the attacker, sending crafted HTTP requests toward the target over interface eth0 — mirroring a simplified real-world scenario in which a SOC analyst monitors a web-facing server for malicious inbound traffic.

Unauthorized SSH Login Detection & Alerting — Splunk

LAB REPORT

Ingested Ubuntu SSH auth logs into Splunk, built a search to surface failed password attempts, and configured a real-time alert so any unauthorized login attempt triggers immediate notification for rapid response.

LOG SOURCE/var/log/auth.log (Linux Secure)
SEARCH QUERYsource="/var/log/auth.log" "Failed password"
ALERT TYPEReal-time · Severity: Medium
Splunk Ubuntu Server Kali Linux (SSH client)
Read Full Project Report

Step 1 — Connect via SSH in Kali

Initiated an SSH connection from the Kali machine toward the Ubuntu target. An incorrect password at this stage is expected and used deliberately to generate a failed-login event for later detection.

Step 2 — Login to Splunk

Logged into the Splunk web interface to begin configuring log ingestion and search.

Step 3 — Ensure Ubuntu SSH Logs Are Ingested into Splunk

  • Settings → Add Data → Monitor → Files & Directories
  • File or Directory: /var/log/auth.log
  • Source Type: Operating System → Linux Secure
  • Review → Submit → Start Searching

Searched for failed SSH login attempts using:

source="/var/log/auth.log" "Failed password"

This search surfaces every recorded event where an incorrect password attempt was made against the SSH service.

Step 4 — Configure the Failed-Login Alert

  • Save As → Alert
  • Title: Failed log Attempt
  • Description: Detection and alerting of unauthorized SSH login attempts using Splunk
  • Alert type: Real time · Expires: 2 minutes
  • Trigger Action: Add to Triggered Alerts · Severity: Medium → Save

Once saved, any subsequent wrong-password SSH attempt appears immediately on the Splunk Alerts page, allowing the attacker's source details to be tracked via View Results.

Conclusion

By setting up this failed-login alert, an immediate notification is generated whenever an unknown person attempts to log in — allowing quick identification of the attacker's details and prompt action to prevent unauthorized access.

DoS, Nmap & Path Traversal Alerting — Splunk

LAB REPORT

Three linked exercises: enabled UFW firewall protection against a simulated SYN flood (DoS) attack, built Splunk searches to surface DoS/UFW events and Nmap reconnaissance, and configured a path traversal alert against a vulnerable PHP endpoint.

PATH TRAVERSAL TARGETview.php?page=../../../etc/passwd

Read Full Project Report

Report A — DoS Attack Alerting

Step 1: Started the Ubuntu Server and connected to Splunk.

Step 2: Connected to Splunk via Firefox using the target's IP address.

Step 3 — Enable the Firewall:

sudo apt install apache2 -y systemctl enable apache2 sudo systemctl start apache2 sudo ufw enable

Once UFW is enabled, the attacker's IP address gets blocked. From Kali, an SSH connection was established and a SYN flood was simulated:

sudo hping3 -S --flood -V -p 80 10.0.2.10

This overloads the target, causing the Apache web page to slow or fail to reload — Ctrl+C stops the flood so the firewall config can refresh.

Step 4 — View DoS Events: Splunk → Settings → Add Data → Monitor → Files & Directories → /var/log/kern.log → Source Type: Linux Secure → Review → Submit.

source="/var/log/kern.log" "UFW ALLOW" DPT=80 | stats count by SRC

Step 5: Saved the search as an Alert so any DoS attack event triggers an immediate notification.

Conclusion: Configuring DoS alerts strengthens the security framework by enabling continuous monitoring of server logs and network activity — abnormal traffic volume is flagged early, minimizing downtime and improving incident response.

Report B — Nmap Scan Detection

Step 1–2: Started the Ubuntu Server and connected to Splunk via Firefox.

Step 3 — Alert Setup: Ran an Nmap scan from Kali against the target, then searched Splunk for UFW Block events. An alert was configured to trigger whenever an Nmap scan is detected.

Conclusion: Since Nmap is commonly used for reconnaissance ahead of an attack, detecting scan activity early lets the security team respond before exploitation — strengthening the overall monitoring framework.

Report C — Path Traversal Alerting

Step 1: Connected via SSH in Kali and started Splunk:

sudo /opt/splunk/bin/splunk start --accept-license --answer-yes --run-as-root

Step 2: Confirmed successful Splunk login.

Step 3 — Install a vulnerable PHP endpoint:

sudo apt install php libapache2-mod-php -y

Added a view.php file to the web root.

Step 4 — Trigger Path Traversal: From Firefox, navigated to:

http://10.0.2.10/view.php?page=../../../etc/passwd

Step 5 — View Events: Settings → Add Data → Monitor → Files & Directories → /var/log/apache2/access.log to surface the traversal request in Splunk for alerting.
